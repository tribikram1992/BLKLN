## 1. Executive Summary

The existing application supports manual Journal Certification by a Preparer and Approver. This architecture introduces a standalone Account Reconciliation module that can be integrated into the existing application without disrupting the current Journal Certification workflow.

The enhancement introduces the following major capabilities:

1. Account Reconciliation manual certification.
2. Local Admin and System Admin account-file upload.
3. System Admin assignment queue.
4. Manual Preparer and Approver assignment.
5. Preparer reconciliation-item and supporting-document management.
6. Approver approval and rejection workflow.
7. Zero-balance System Certification.
8. AI-based Excel-versus-screen validation for Journal Details and Account Reconciliation Details.
9. Full audit, RBAC, notification, and deployment integration.
10. Reuse of the existing UI styles, fonts, CSS tokens, header, footer, folder structure, and coding standards.

The module is additive. Existing Journal Certification tables, APIs, business workflows, and screens remain unchanged, except for the additive AI validation action on the Journal Details page.

## 3. Architecture Principles

The following principles are mandatory:

1. No physical deletion of business records.
2. Use `is_active`, status fields, or equivalent soft-delete controls.
3. Certification records are immutable.
4. Audit records are immutable.
5. AI validation records are immutable.
6. Business-key foreign keys must be used where consistent with the existing application.
7. A Preparer cannot be the Approver for the same reconciliation.
8. All mutable tables must contain `created_at` and `updated_at`.
9. Immutable tables must contain `created_at` and must not contain `updated_at`.
10. SQL migrations must be idempotent.
11. Existing JWT, RBAC, active-role, and capability controls must be reused.
12. Existing frontend and backend coding conventions must be followed.
13. Existing Baxter branding, fonts, header, footer, CSS tokens, and component styles must be reused.
14. System Certification must remain fully auditable.
15. AI validation failures must not block manual certification unless a future configuration explicitly makes validation mandatory.

## 5. End-to-End Account Reconciliation Flow

### 5.1 File Upload

A Local Admin, Business Admin, or System Admin uploads an Accounts text file.

The system performs the following actions:

1. Validates the file type.
2. Calculates the SHA-256 file hash.
3. Stores the original file.
4. Creates an `account_file_load` row.
5. Starts parsing.
6. Validates required columns.
7. Normalizes dates, booleans, currencies, and balances.
8. Creates one reconciliation record per valid account row.
9. Evaluates the active Zero-Balance System Certification rule.
10. Sends non-auto-certified accounts to the System Admin queue.
11. Updates upload counters and processing status.
12. Records upload and parsing audit events.

### 5.2 System Admin Queue

Accounts that do not qualify for System Certification are created with:

```text
status = NOT_ASSIGNED
```

These records appear in the System Admin queue.

### 5.3 Manual Assignment

The System Admin or another authorized administrator manually provides:

- Preparer.
- Approver.
- Optional Reviewer.

The system validates:

- The selected users exist.
- The selected users are active.
- The selected users hold compatible roles.
- The Preparer and Approver are different users.

After successful assignment, the reconciliation moves to:

```text
NOT_PREPARED
```

### 5.4 Preparer Processing

The assigned Preparer opens the Reconciliation Details screen and can:

- Review account balances and account attributes.
- Add reconciling items.
- Add comments.
- Upload supporting documents.
- Add hyperlinks.
- Run AI Excel-versus-screen validation.
- Save progress.
- Certify the reconciliation.

After certification, the status becomes:

```text
PREPARED
```

### 5.5 Approver Processing

The assigned Approver opens the same Reconciliation Details route with Approver-specific actions.

The Approver can:

- Review all account information.
- Review Preparer items.
- Review comments and supporting documents.
- Add Approver comments and documents.
- Run AI validation.
- Approve the reconciliation.
- Reject the reconciliation with a reason.

Approval changes the status to:

```text
APPROVED
```

Rejection changes the status to:

```text
REJECTED
```

A rejected reconciliation returns to the Preparer for correction and recertification.

## 6. Reconciliation Status Model

The Account Reconciliation module uses seven statuses.

### 6.1 `NOT_ASSIGNED`

The reconciliation was created by the parser but has not been assigned to a Preparer and Approver.

### 6.2 `NOT_PREPARED`

The reconciliation has been assigned and is waiting for the Preparer.

### 6.3 `PREPARED`

The Preparer certified the reconciliation. The reconciliation is waiting for the Approver.

### 6.4 `APPROVED`

The Approver approved the reconciliation. This is a terminal state.

### 6.5 `REJECTED`

The Approver rejected the reconciliation. The reconciliation returns to the Preparer.

### 6.6 `DECERTIFIED`

The Preparer or an authorized administrator retracted a previously prepared reconciliation. The reconciliation requires recertification.

### 6.7 `SYSTEM_CERTIFIED`

The reconciliation was automatically certified by the configured Zero-Balance rule. This is a terminal state.

### 6.8 Transition Matrix

| From | Action | Actor | To |
|---|---|---|---|
| File parsing | System certify | System | `SYSTEM_CERTIFIED` |
| File parsing | Queue | System | `NOT_ASSIGNED` |
| `NOT_ASSIGNED` | Assign | Admin | `NOT_PREPARED` |
| `NOT_PREPARED` | Certify | Preparer | `PREPARED` |
| `PREPARED` | Approve | Approver | `APPROVED` |
| `PREPARED` | Reject | Approver | `REJECTED` |
| `PREPARED` | Decertify | Preparer or authorized Admin | `DECERTIFIED` |
| `REJECTED` | Recertify | Preparer | `PREPARED` |
| `DECERTIFIED` | Recertify | Preparer | `PREPARED` |

Terminal statuses:

```text
APPROVED
SYSTEM_CERTIFIED
```

## 8. Zero-Balance System Certification

### 8.1 Default Rule

The default rule is:

```text
GL Account Balance is zero or null
AND
Activity in Period is false
```

When the rule matches:

```text
status = SYSTEM_CERTIFIED
```

### 8.2 Configuration-Driven Design

The Zero-Balance rule must not be hard-coded. It should be stored in `account_zero_balance_rule` and selected through application configuration.

Recommended rule attributes:

- Rule code.
- Rule name.
- Description.
- Require zero balance.
- Treat null as zero.
- Require no activity.
- Zero tolerance.
- Applicable assignment type.
- Active flag.

### 8.3 Evaluation Logic

```python
balance_is_zero = abs(gl_account_balance or 0) <= zero_tolerance
activity_is_allowed = not require_no_activity or activity_in_period is False
assignment_type_allowed = configured_type is None or assignment_type == configured_type

system_certify = balance_is_zero and activity_is_allowed and assignment_type_allowed
```

### 8.4 System Certification Transaction

Within the same transaction, the system must:

1. Create or update the reconciliation.
2. Set `status = SYSTEM_CERTIFIED`.
3. Set `is_zero_balance = true`.
4. Store the applied rule code.
5. Set the final certification state.
6. Set completion and closure fields.
7. Create an immutable certification row with action `SYSTEM_CERTIFY`.
8. Create an immutable audit record.
9. Increment the file-level System Certified counter.

### 8.5 System Certification Restrictions

A `SYSTEM_CERTIFIED` reconciliation:

- Does not enter the Admin assignment queue.
- Does not require a Preparer.
- Does not require an Approver.
- Cannot be manually certified from the standard UI.
- Is read-only.
- Appears in reporting.
- Displays a System Certified status badge.
- Displays an immutable System Certification history row.

### 8.6 Edge Cases

| Scenario | Result |
|---|---|
| Null balance and no activity | System Certified when null is configured as zero |
| Zero balance and no activity | System Certified |
| Zero balance with activity | Manual queue |
| Non-zero balance and no activity | Manual queue |
| Rule inactive | Manual queue |
| Unsupported assignment type | Manual queue |


### 11.2 Validation

The backend must validate:

- Selected users are active.
- Selected users are authorized for the appropriate role.
- Preparer and Approver are not the same user.
- The reconciliation is in an assignable status.

### 11.3 Successful Assignment

On assignment, the system must:

1. Create Preparer assignment with sequence 1.
2. Create Approver assignment with sequence 2.
3. Optionally create Reviewer assignment with sequence 3.
4. Update denormalized user references on the reconciliation header.
5. Change status from `NOT_ASSIGNED` to `NOT_PREPARED`.
6. Add an immutable assignment audit entry.
7. Queue a notification for the Preparer.

## 18. AI Excel-Versus-Screen Validation

### 18.1 Supported Contexts

The same AI validation service supports:

```text
JOURNAL
ACCOUNT
```

Context mapping:

| Context | Context ID | Screen Data | Source Document |
|---|---|---|---|
| `JOURNAL` | Journal ID | Journal header and lines | Journal supporting document |
| `ACCOUNT` | Reconciliation ID | Account header and reconciling items | Account supporting document |

### 18.2 UI Action

The Supporting Documents area should provide:

```text
Validate with AI
```

The action can be displayed at document level and at panel level.

### 18.3 Validation Flow

```text
User selects Excel or CSV supporting document
               |
               v
Backend authorization
               |
               v
Load screen data from database
               |
               v
Load and parse uploaded document
               |
               v
Normalize dates, strings, identifiers, and amounts
               |
               v
Compare using server-side deterministic logic
               |
               v
Send minimized discrepancy descriptors to AI
               |
               v
Classify discrepancy severity and explanation
               |
               v
Persist immutable validation result
               |
               v
Display results to user
```

### 18.4 Server-Side Responsibilities

The server must perform:

- Excel or CSV parsing.
- Decimal conversion.
- Rounding.
- Tolerance evaluation.
- Date normalization.
- String trimming.
- Identifier matching.
- Row count comparison.
- Match count calculation.
- Discrepancy count calculation.

The AI should be used only for:

- Semantic column mapping.
- Ambiguous row alignment.
- Severity classification.
- Short discrepancy explanation.

### 18.5 Result Statuses

Recommended statuses:

```text
PENDING
MATCH
DISCREPANCIES_FOUND
ERROR
TIMEOUT
DECLINED
```

### 18.6 Result Fields

- Validation ID.
- Context Type.
- Context ID.
- Source Document ID.
- Source File Name.
- Rows Compared.
- Fields Compared.
- Match Count.
- Discrepancy Count.
- Result Status.
- Discrepancy List.
- Error Message.
- Model Used.
- Tokens Used.
- Latency.
- Requested By.
- Requested Role.
- Created At.

### 18.7 Discrepancy Structure

```json
{
  "field": "GL Account Balance",
  "screen_value": "7000.00",
  "file_value": "7000.10",
  "row_ref": "Account 41114058618",
  "severity": "HIGH",
  "note": "The values differ by 0.10."
}
```

### 18.8 AI Validation UI

When all values match:

```text
No discrepancies found.
```

When differences exist, the table should show:

- Field.
- Screen Value.
- File Value.
- Row Reference.
- Difference.
- Severity.
- Note.

### 18.9 AI Governance

1. AI validation must not update financial data.
2. Raw ledgers should not be unnecessarily sent to the model.
3. Prompts should contain minimized structured data.
4. Every validation run must be audited.
5. Validation errors must not corrupt the certification transaction.
6. Validation should remain advisory unless configured as mandatory.
7. Authorization must be enforced at both route and record level.

-- ── Segregation of duties ───────────────────────────────────────────────
-- One person must never hold both the PREPARER and APPROVER assignment on the
-- same journal: they could prepare it, switch to their approver role, and
-- approve their own work.
--
-- This cannot be a CHECK constraint — the rule spans two rows of this table —
-- so it is a trigger. jde_user_dependency_mapping already carries an equivalent
-- CHECK (chk_jde_diff_user), but that only governs the default pairing used at
-- upload time; a direct or corrected assignment bypassed it entirely.
CREATE OR REPLACE FUNCTION enforce_assignment_sod()
RETURNS TRIGGER AS $$
DECLARE
    conflicting_role VARCHAR(50);
BEGIN
    IF NEW.role_code NOT IN ('PREPARER', 'APPROVER') THEN
        RETURN NEW;
    END IF;

    SELECT ja.role_code INTO conflicting_role
    FROM journal_assignment ja
    WHERE ja.journal_id       = NEW.journal_id
      AND ja.assigned_user_id = NEW.assigned_user_id
      AND ja.role_code        <> NEW.role_code
      AND ja.role_code IN ('PREPARER', 'APPROVER')
      AND ja.id               <> COALESCE(NEW.id, -1)
    LIMIT 1;

    IF conflicting_role IS NOT NULL THEN
        RAISE EXCEPTION
            'Segregation of duties: user % is already the % on journal % and cannot also be the %',
            NEW.assigned_user_id, conflicting_role, NEW.journal_id, NEW.role_code
            USING ERRCODE = 'check_violation';
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_journal_assignment_sod ON journal_assignment;
CREATE TRIGGER trg_journal_assignment_sod
    BEFORE INSERT OR UPDATE ON journal_assignment
    FOR EACH ROW EXECUTE FUNCTION enforce_assignment_sod();

    -- rewording it afterwards would misrepresent what was said at the point of
    -- the decision. Authorship alone is not a sufficient rule: a journal
    -- rejected back to its preparer would otherwise let them rewrite the
    -- comments the approver had already acted on.

-- =============================================================================
-- 9.12b  journal_comment_history   (append-only audit trail for comments)
-- =============================================================================
-- One row per action. CREATE stores the original text as new_text with
-- old_text NULL; EDIT stores both sides of the change.
--
-- performed_by_role is captured at the moment of the action, not read back from
-- the user later: a user may hold several roles and switch between them, so the
-- role that made the edit must be frozen into the record.
--
-- Append-only: never UPDATE or DELETE. This is the evidence the live thread
-- deliberately hides.
CREATE TABLE IF NOT EXISTS journal_comment_history (
    id                       BIGSERIAL PRIMARY KEY,
    history_id               VARCHAR(100) UNIQUE NOT NULL,
    comment_id               VARCHAR(100) NOT NULL REFERENCES journal_comment(comment_id),
    journal_id               VARCHAR(100) NOT NULL REFERENCES journal_header(journal_id),
    action                   VARCHAR(20)  NOT NULL,
    old_text                 TEXT,
    new_text                 TEXT         NOT NULL,
    performed_by             VARCHAR(100) NOT NULL REFERENCES users(user_id),
    performed_by_display_name VARCHAR(255),
    performed_by_role        VARCHAR(50)  NOT NULL REFERENCES roles(role_code),
    performed_at             TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    created_at               TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW(),
    -- NO updated_at — history rows are immutable
    CONSTRAINT chk_jch_action CHECK (action IN ('CREATED', 'EDITED')),
    -- A CREATED row has nothing before it; an EDITED row must record what it replaced.
    CONSTRAINT chk_jch_old_text CHECK (
        (action = 'CREATED' AND old_text IS NULL)
        OR (action = 'EDITED' AND old_text IS NOT NULL)
    )
);

CREATE INDEX IF NOT EXISTS idx_jchistory_journal_at
    ON journal_comment_history(journal_id, performed_at DESC);
CREATE INDEX IF NOT EXISTS idx_jchistory_comment_id
    ON journal_comment_history(comment_id);

-- =============================================================================
-- ══ MODULE: ACCOUNT RECONCILIATION (module 2 of 8) ══
-- Per Docs/ArchitecturePlanV2.md Section 6 (spec) and Section 1.2 (module
-- contract). Table prefix account_*. Mirrors journal_* conventions exactly:
--   - Business-key FKs only (user_id, role_code, team_id, reconciliation_id,
--     file_load_id) — never surrogate BIGSERIAL PKs across tables.
--   - IF NOT EXISTS on every CREATE TABLE / CREATE INDEX.
--   - Mutable tables: created_at + updated_at, both NOT NULL DEFAULT NOW().
--   - Immutable tables (account_certification, account_audit_log,
--     account_rule_evaluation_log): created_at only — no updated_at, no
--     UPDATE/DELETE ever.
--   - Soft-delete via is_active/status; no physical deletes anywhere.
--   - account_rule / account_rule_evaluation_log follow the generic
--     cross-module rule-engine pattern (Section 4), not a bespoke
--     account_zero_balance_rule table — zero-balance auto-cert is rule #1.
-- =============================================================================

-- =============================================================================
-- 10.2  account_reconciliation  (the reconciliation header — mirrors journal_header)
--       One row per account per period. Lands in the System Admin queue after
--       upload (NOT_ASSIGNED) unless zero-balance/no-activity, in which case
--       it is auto-certified (SYSTEM_CERTIFIED). 7-status FSM.
-- =============================================================================
CREATE TABLE IF NOT EXISTS account_reconciliation (
    id                      BIGSERIAL PRIMARY KEY,
    reconciliation_id       VARCHAR(100) UNIQUE NOT NULL,
    source_file_id          VARCHAR(100) NOT NULL REFERENCES account_file_load(file_load_id),

    -- ── From Accounts import file (BL_Accounts_Import_Template, AR-03) ───────
    entity_unique_id        VARCHAR(100) NOT NULL,
    account_number          VARCHAR(100) NOT NULL,
    key3                    VARCHAR(50),
    key4                    VARCHAR(50),
    key5                    VARCHAR(50),
    key6                    VARCHAR(50),
    key7                    VARCHAR(50),
    key8                    VARCHAR(50),
    key9                    VARCHAR(50),
    key10                   VARCHAR(50),
    account_description     VARCHAR(500),
    account_reference       VARCHAR(50),
    assignment_type         VARCHAR(10),                  -- 'A' = Account Reconciliation
    account_type            VARCHAR(50),
    active_account          BOOLEAN NOT NULL DEFAULT TRUE,
    activity_in_period      BOOLEAN NOT NULL DEFAULT FALSE, -- auto-cert driver
    alternate_currency      VARCHAR(10),                    -- raw file column; superseded by alternate_currency_display
    account_currency        VARCHAR(10),
    period_end_date         DATE NOT NULL,
    period_label            VARCHAR(7),                     -- MM/YYYY (denormalized)

    -- ── Balances ─────────────────────────────────────────────────────────────
    gl_reporting_balance    NUMERIC(20, 2),
    gl_alternate_balance    NUMERIC(20, 2),
    gl_account_balance      NUMERIC(20, 2),                 -- nullable: a blank balance in the source file is a real business value ("null balance"), not a data error — the zero-balance rule's treat_null_as_zero predicate depends on being able to distinguish NULL from 0
    gl_account_balance_usd  NUMERIC(20, 2),
    bl_currency_rate_usd    NUMERIC(18, 8) DEFAULT 1,

    -- ── Computed / Admin-set-once-at-assignment fields (ArchitecturePlanV2 §6.2–6.4) ──
    account_name               VARCHAR(500),   -- computed at parse time: colA..colI joined with '-', blanks preserved as empty positions (decision log #6)
    risk_rating                VARCHAR(20)  NOT NULL DEFAULT 'NONE',
    reconciliation_frequency   VARCHAR(20)  NOT NULL DEFAULT 'MONTHLY',  -- stored/selectable now; not enforced until FREQUENCY_QUEUE_FILTER rule is activated (decision log #8)
    alternate_currency_display VARCHAR(10)  NOT NULL DEFAULT 'USD',      -- always 'USD', sourced from app_config.account_alternate_currency_default, never the file's own column

    -- ── Denormalized display / grouping ──────────────────────────────────────
    company_code            VARCHAR(50),
    region                   VARCHAR(100),
    team_id                  VARCHAR(100) REFERENCES teams(team_id),   -- shared table, no new schema (decision log #9)
    template                 VARCHAR(255) NOT NULL DEFAULT 'Account Reconciliation',
    header_status_display    VARCHAR(255),
    final_certification_state VARCHAR(100),
    is_completed             BOOLEAN NOT NULL DEFAULT FALSE,

    -- ── Assignment (populated by System Admin manually — account_admin_manual_assignment=true) ──
    preparer_user_id         VARCHAR(100) REFERENCES users(user_id),
    approver_user_id         VARCHAR(100) REFERENCES users(user_id),
    reviewer_user_id         VARCHAR(100) REFERENCES users(user_id),

    -- ── Presence flags (updated by item/comment/document services) ───────────
    has_items                BOOLEAN NOT NULL DEFAULT FALSE,
    has_comments             BOOLEAN NOT NULL DEFAULT FALSE,
    has_documents             BOOLEAN NOT NULL DEFAULT FALSE,

    -- ── Workflow status (7-status FSM, AR-04 §4.1–4.2) ────────────────────────
    -- NOT_ASSIGNED     : parsed, sitting in SYSTEM_ADMIN queue (unassigned)
    -- NOT_PREPARED     : admin assigned preparer+approver, awaiting preparer
    -- PREPARED         : preparer certified, awaiting approver
    -- APPROVED         : approver approved (terminal)
    -- REJECTED         : approver rejected; preparer must re-certify
    -- DECERTIFIED      : preparer retracted; preparer must re-certify
    -- SYSTEM_CERTIFIED : zero-balance / no-activity auto-certification (terminal)
    status                   VARCHAR(50) NOT NULL DEFAULT 'NOT_ASSIGNED',
    is_zero_balance          BOOLEAN NOT NULL DEFAULT FALSE,
    auto_cert_rule_id         VARCHAR(100),   -- account_rule.rule_id that fired, if any

    CONSTRAINT chk_ar_status CHECK (
        status IN (
            'NOT_ASSIGNED','NOT_PREPARED','PREPARED','APPROVED',
            'REJECTED','DECERTIFIED','SYSTEM_CERTIFIED'
        )
    ),
    CONSTRAINT chk_ar_diff_user CHECK (
        preparer_user_id IS NULL
        OR approver_user_id IS NULL
        OR preparer_user_id <> approver_user_id
    ),
    CONSTRAINT chk_ar_risk_rating CHECK (risk_rating IN ('NONE','LOW','MEDIUM','HIGH')),
    CONSTRAINT chk_ar_frequency CHECK (reconciliation_frequency IN ('MONTHLY','QUARTERLY','ANNUAL')),

    -- ── Lifecycle ────────────────────────────────────────────────────────────
    is_active                BOOLEAN NOT NULL DEFAULT TRUE,
    created_by                VARCHAR(100) REFERENCES users(user_id),
    created_at                TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at                TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    closed_at                 TIMESTAMPTZ,

    -- One reconciliation per account per entity per period
    UNIQUE(entity_unique_id, account_number, period_end_date, account_currency)
);

CREATE INDEX IF NOT EXISTS idx_ar_period        ON account_reconciliation(period_label);
CREATE INDEX IF NOT EXISTS idx_ar_status        ON account_reconciliation(status);
CREATE INDEX IF NOT EXISTS idx_ar_period_status ON account_reconciliation(period_label, status);
CREATE INDEX IF NOT EXISTS idx_ar_company       ON account_reconciliation(company_code);
CREATE INDEX IF NOT EXISTS idx_ar_region        ON account_reconciliation(region);
CREATE INDEX IF NOT EXISTS idx_ar_team          ON account_reconciliation(team_id);

--        ZERO_BALANCE_AUTO_CERT) is rule #1, proving the pattern — NOT a

--         "applies_to_assignment_type":"A"}.

    rule_name            VARCHAR(255) NOT NULL,
    description           TEXT,
    scope_json            JSONB,                   -- {"roles":[...],"pages":[...],"company_codes":[...], <predicate config>}
    is_active             BOOLEAN NOT NULL DEFAULT TRUE,
    effective_from         DATE,
    effective_to           DATE,
    created_at              TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT NOW()

-- =============================================================================
-- 10.12  ai_validation_log  (IMMUTABLE append-only audit, alongside ai_session_log)
--        AI Excel-vs-Screen Discrepancy Validation -- used on BOTH the Journal
--        Details page and the Account Reconciliation Details page. Per
--        ArchitecturePlanV2.md Section 5.2: NOT a new AI subsystem -- two more
--        tools (compare_uploaded_file, highlight_discrepancy) folded into the
--        existing agent tool-use loop. context_type discriminates JOURNAL vs
--        ACCOUNT so one table serves both detail pages.
--        DATA GOVERNANCE: the AI never mutates financial data and never
--        receives raw ledgers -- all arithmetic/normalisation happens
--        server-side (Decimal, tolerance from app_config); the model receives
--        only minimized, already-computed discrepancy descriptors.
-- =============================================================================
CREATE TABLE IF NOT EXISTS ai_validation_log (
    id                  BIGSERIAL PRIMARY KEY,
    validation_id       VARCHAR(100) UNIQUE NOT NULL,

    -- What was validated
    context_type        VARCHAR(50) NOT NULL,   -- JOURNAL | ACCOUNT
    context_id          VARCHAR(100) NOT NULL,  -- journal_id or reconciliation_id

    -- Source of the "truth" file the user uploaded to be checked
    source_document_id  VARCHAR(100),           -- journal_document.document_id OR account_document.document_id
    source_file_name    VARCHAR(500),
    source_file_hash    VARCHAR(64),

    -- AI request/response metadata (NO raw financial values persisted here)
    requested_by        VARCHAR(100) NOT NULL REFERENCES users(user_id),
    requested_role      VARCHAR(50)  REFERENCES roles(role_code),
    model_used          VARCHAR(100),
    tokens_used         INTEGER,
    latency_ms          INTEGER,

    -- Result summary (arithmetic done server-side, AI classifies only)
    rows_compared       INTEGER NOT NULL DEFAULT 0,
    fields_compared     INTEGER NOT NULL DEFAULT 0,
    match_count         INTEGER NOT NULL DEFAULT 0,
    discrepancy_count   INTEGER NOT NULL DEFAULT 0,
    result_status       VARCHAR(50) NOT NULL DEFAULT 'PENDING',
    -- Values: PENDING | MATCH | DISCREPANCIES_FOUND | ERROR | TIMEOUT | DECLINED

    -- Structured, minimized discrepancy payload for UI rendering:
    -- [{ field, screen_value, file_value, row_ref, severity, note }]
    discrepancies_json  JSONB,
    error_message       TEXT,

    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
    -- NO updated_at -- immutable, like ai_session_log
);

CREATE INDEX IF NOT EXISTS idx_aiv_context      ON ai_validation_log(context_type, context_id);
CREATE INDEX IF NOT EXISTS idx_aiv_requested_by ON ai_validation_log(requested_by);
CREATE INDEX IF NOT EXISTS idx_aiv_result       ON ai_validation_log(result_status);
CREATE INDEX IF NOT EXISTS idx_aiv_created_at   ON ai_validation_log(created_at DESC);
CREATE INDEX IF NOT EXISTS idx_aiv_source_doc   ON ai_validation_log(source_document_id);
