## 1. Purpose

This document defines the updated Phase 1 architecture for the Journal Certification Pilot application.

The design is based on the provided journal text file, journal template, requirement sheet, and screenshot-driven UI behavior. The Phase 1 application will focus on a small but enterprise-ready workflow:

1. Manual upload of a tab-delimited journal text file.
2. Parsing the file into journal header and journal line records.
3. Routing journals to a Preparer/Reconciler work queue.
4. Allowing the Preparer/Reconciler to review, attach documents, add comments, and certify.
5. Routing certified journals to an Approver work queue.
6. Allowing the Approver to review, certify, or reject.
7. Supporting users with multiple roles through a top-right user/role dropdown.
8. Enforcing that the same user cannot be both preparer and approver for the same journal.
9. Supporting document upload, document preview, and direct download.
10. Showing an Admin currency conversion immutable grid.
11. Keeping all key table schemas ready for Phase 1 and future extension.

## 2. Confirmed Understanding From Uploaded Files

### 2.1 Journal Text File Format

The uploaded journal text file is tab-delimited. Each journal row contains 27 fields separated by the tab character `\t`.

Parser configuration:

```python
delimiter = "\t"
expected_column_count = 27
```

The parser must not use comma, pipe, or space-based parsing because several fields have leading spaces, trailing spaces, and padded blanks.

### 2.2 Journal Template Fields

The Journal Template defines the following 27 fields:

1. DocumentType
2. DocumentNumber
3. GLDate
4. PeriodNumber
5. FiscalYear
6. BatchNumber
7. BatchDate
8. LedgerType
9. ReverseOrVoid
10. Preparer
11. BusinessUnit
12. ObjectAccount
13. Subsidiary
14. Subledger
15. Amount
16. Explanation1
17. Explanation2
18. CompanyCode
19. BatchType
20. Currency
21. ExchangeRate
22. JE Line Number
23. SublederType
24. GLPostStatus
25. AssetNumber
26. Last Modified By
27. AccountDescription

### 2.3 Screenshot-Based UI Understanding

The screenshot document shows a enterprise-style layout with these key patterns:

- A post-login landing screen.
- A journal grid where user actions appear in the first column area.
- A detailed journal view containing header details, line items, comments, supporting documents, hyperlinks, and certification controls.
- A certification/audit trace area showing who acted, when they acted, and what action/status was captured.
- A role-based experience where users see actions according to their current responsibility.

For Phase 1, the UI should follow this pattern but only implement the minimum necessary Preparer/Reconciler, Approver, and Local Admin flows.

## 8. Critical Workflow Rule: Same User Cannot Prepare and Approve Same Journal

### 8.1 Business Rule

The same user must not certify the same journal as both Preparer/Reconciler and Approver.

Invalid assignment:

```text
Journal: JRN001
Preparer/Reconciler: USR001
Approver: USR001
```

Valid assignment:

```text
Journal: JRN001
Preparer/Reconciler: USR001
Approver: USR002
```

### 8.2 Where to Enforce

Enforce this rule in three places:

1. During journal assignment after file upload.
2. During Preparer certification before moving to Approver.
3. During Approver certification before final close.

### 8.3 Backend Validation

```python
if preparer_user_id == approver_user_id:
    raise BusinessValidationException(
        "Preparer/Reconciler and Approver cannot be the same user for the same journal."
    )
```

### 8.4 Database Check Strategy

A direct SQL CHECK constraint is difficult because assignments are stored in multiple rows. Use application validation and add a database trigger later if needed.

For Phase 1, use:

```text
Application validation + integration test coverage
```

## 9. Period and Filter Strategy

### 9.1 Top Filter: Period

Period is the primary mandatory filter at the top of the journal screen.

Format:

```text
MM/YYYY
```

Example:

```text
07/2026
```

Purpose:

```text
Performance optimization and UI rendering control
```

The user must select period first. Journals are loaded only for the selected period.

### 9.2 Screen Layout

```text
+------------------------------------------------------------+
| Period * [ 07/2026 ▼ ]                                    |
+------------------------------------------------------------+

+------------------------------------------------------------+
| Secondary grid filters                                     |
| Journal ID | Document No | Company | Currency | Status ... |
+------------------------------------------------------------+

+------------------------------------------------------------+
| Journal Grid                                               |
+------------------------------------------------------------+
```

### 9.3 Primary Query Pattern

Preparer/Reconciler:

```sql
SELECT j.*
FROM journal_header j
JOIN journal_assignment a ON a.journal_id = j.journal_id
WHERE j.journal_period = :period
  AND a.assigned_user_id = :logged_in_user
  AND a.role_code = 'PREPARER_RECONCILER'
  AND j.status IN ('PENDING_PREPARER', 'PREPARER_IN_PROGRESS', 'REJECTED');
```

Approver:

```sql
SELECT j.*
FROM journal_header j
JOIN journal_assignment a ON a.journal_id = j.journal_id
WHERE j.journal_period = :period
  AND a.assigned_user_id = :logged_in_user
  AND a.role_code = 'APPROVER'
  AND j.status = 'PENDING_APPROVER';
```

### 9.4 Secondary Filters

Secondary filters should appear with the grid, similar to the previous screenshot-style filter behavior.

Examples:

```text
Journal ID
Document Number
Batch Number
Company Code
Currency
Status
Preparer
Approver
Template
Team
```

### 9.5 Auto-Filter Rule

Auto-filter only when the typed value is more than 2 characters.

Rule:

```text
Length 0: clear filter
Length 1: do not trigger search
Length 2: do not trigger search
Length 3 or more: trigger auto-filter
```

Recommended UI debounce:

```text
500 ms
```

This gives a responsive UI without calling the backend on every keystroke.

### 9.6 Filter Implementation Approach

Only the Period filter causes an API call and database lookup. All other grid filters are handled in the browser using React, Next.js, and JavaScript against the period-loaded dataset.

Recommended Phase 1 approach:

```text
Period filter: server-side mandatory
Secondary filters: client-side only
No database hit for Journal ID, Document Number, Company Code, Currency, Status, Preparer, Approver, Template, or Team filters
```

Data flow:

```text
User selects Period MM/YYYY
        |
        v
Frontend calls work queue API once
        |
        v
Backend queries database by period, active role, and assigned user
        |
        v
Frontend stores returned rows in React state
        |
        v
Secondary filters run purely in UI memory
```

Frontend state model:

```typescript
const [allJournals, setAllJournals] = useState<JournalRow[]>([]);
const [filteredJournals, setFilteredJournals] = useState<JournalRow[]>([]);
const [filters, setFilters] = useState<JournalGridFilters>({});
```

Filtering rule:

```text
Length 0: clear that filter and show records from the loaded period dataset
Length 1: do not apply filter
Length 2: do not apply filter
Length 3 or more: apply client-side filter
```

Use a 300 to 500 ms debounce only to avoid unnecessary React re-rendering while the user is typing. The debounce must not call the backend for secondary filters.

## 10. JDE ADID-Based Dependency Mapping

### 10.1 Why This Mapping Is Needed

The journal source text file contains the ADID of the Preparer in the `Preparer` field. The application should not treat that value as only display text. It must use that ADID to identify the application user who receives the journal in the Preparer/Reconciler queue.

Once the Preparer is identified, the application must identify the Approver using the dependency mapping. This ensures that the journal workflow is not hardcoded and can follow the actual JDE/BlackLine dependency relationship.

### 10.2 Mapping Flow

```text
Journal text file uploaded by Local Admin
        |
        v
Parser reads Preparer field from text file
        |
        v
Preparer field value is treated as Preparer ADID
        |
        v
System resolves Preparer ADID to users.adid
        |
        v
System looks up dependency mapping for Preparer ADID
        |
        v
System resolves Approver ADID to users.adid
        |
        v
System validates Preparer user != Approver user
        |
        v
System creates journal_assignment rows
```

### 10.3 Role Codes From Dependency Mapping

The dependency relationship uses operational role codes:

```text
BLPREPARER
BLAPPROVER
```

Application role mapping:

```text
BLPREPARER -> PREPARER_RECONCILER
BLAPPROVER -> APPROVER
```



### 10.4 Admin Dependency Mapping Screen

The Admin should be able to view the dependency mapping screen. This screen shows how the system determines who is the Preparer and who is the Approver.

Accessible by active role:

```text
LOCAL_ADMIN
```

The screen is view-only for Phase 1 unless explicitly enabled later for admin maintenance.

Grid columns:

```text
Preparer ADID
Preparer Name
Preparer User ID
Preparer Role Code
Approver ADID
Approver Name
Approver User ID
Approver Role Code
Company Code
Region
Team
Effective From
Effective To
Source System
Source File Name
Active Flag
```

Filter behavior:

```text
Initial screen load calls backend once to load dependency mapping rows.
All bottom/grid filters are UI-only.
No database hit for Preparer ADID, Approver ADID, Company Code, Region, Team, or Active Flag filtering.
Filter is applied in React/Next.js/JavaScript against loaded rows.
Trigger client-side filtering only when the typed value is more than 2 characters.
```

### 10.5 Dependency Mapping API

```http
GET /api/v1/admin/dependency-mappings
```

This endpoint is called only when the Admin opens the dependency mapping screen or refreshes it. UI filters do not call this endpoint.

### 10.6 Assignment Validation Rules

During journal upload and assignment creation:

```text
Preparer ADID must exist in users.adid.
Approver ADID must exist in users.adid.
Preparer must have BLPREPARER mapped to PREPARER_RECONCILER access.
Approver must have BLAPPROVER mapped to APPROVER access.
Preparer user and Approver user must not be the same user.
If dependency mapping is missing, journal should be marked FAILED or ASSIGNMENT_ERROR and shown in upload processing results.
```

Recommended upload error message:

```text
Approver mapping not found for Preparer ADID: <adid>
```

Recommended same-user validation message:

```text
Preparer and Approver cannot be the same user for the same journal.
```

## 13. Header and Line Split Logic

### 13.1 Header Grouping Key

Create one journal header for each unique combination of:

```text
DocumentType
DocumentNumber
GLDate
PeriodNumber
FiscalYear
BatchNumber
BatchDate
LedgerType
CompanyCode
BatchType
Currency
Preparer
```

### 13.2 Line Creation

Each text file row becomes one `journal_line` record.

### 13.3 Debit and Credit Calculation

```text
If Amount > 0, add to Total Debit
If Amount < 0, add absolute value to Total Credit
```

### 13.4 USD Calculation

```text
amount_usd = amount * conversion_rate
```

For header totals:

```text
total_debit_usd = total_debit * conversion_rate
total_credit_usd = total_credit * conversion_rate
```

## 15.21 role_external_mapping

This table maps external/JDE or enterprise-style role codes to the internal application role codes. This is needed because the incoming JDE text file or dependency setup may refer to operational role codes such as `BLPREPARER` and `BLAPPROVER`, while the application internally uses business role codes such as `PREPARER_RECONCILER` and `APPROVER`.

Recommended normalization:

```text
External role code from JDE/dependency area: BLPREPARER
Internal role code: PREPARER_RECONCILER

External role code from JDE/dependency area: BLAPPROVER
Internal role code: APPROVER
```



```sql
CREATE TABLE role_external_mapping (

    source_system VARCHAR(100) NOT NULL DEFAULT 'JDE',
    description TEXT,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
```

## 15.22 jde_user_dependency_mapping

This table maps who the Preparer is and who the Approver is based on the ADID relationship expected from the JDE/source data. The JDE journal text file contains the preparer ADID in the `Preparer` field. The application resolves that ADID to an application user, then finds the assigned approver using this dependency mapping.

Business rules:

```text
The source journal file contains Preparer ADID.
The application resolves Preparer ADID to users.adid.
The dependency mapping resolves Approver ADID for that Preparer ADID.
The application resolves Approver ADID to users.adid.
The Preparer and Approver users must be different.
The Preparer role code from dependency/source is BLPREPARER.
The Approver role code from dependency/source is BLAPPROVER.
```

```sql
CREATE TABLE jde_user_dependency_mapping (
    id BIGSERIAL PRIMARY KEY,
    dependency_id VARCHAR(100) UNIQUE NOT NULL,

    preparer_adid VARCHAR(100) NOT NULL,
    preparer_user_id VARCHAR(100) REFERENCES users(user_id),
    preparer_role_code VARCHAR(100) NOT NULL DEFAULT 'BLPREPARER',

    approver_adid VARCHAR(100) NOT NULL,
    approver_user_id VARCHAR(100) REFERENCES users(user_id),
    approver_role_code VARCHAR(100) NOT NULL DEFAULT 'BLAPPROVER',

    company_code VARCHAR(50),
    region VARCHAR(100),
    team_id VARCHAR(100) REFERENCES team(team_id),
    effective_from DATE,
    effective_to DATE,
    source_system VARCHAR(100) NOT NULL DEFAULT 'JDE',
    source_file_name VARCHAR(500),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT chk_jde_preparer_approver_adid_diff CHECK (preparer_adid <> approver_adid),
    CONSTRAINT chk_jde_preparer_approver_user_diff CHECK (
        preparer_user_id IS NULL
        OR approver_user_id IS NULL
        OR preparer_user_id <> approver_user_id
    )
);
```

## 18. Frontend Folder Structure

The frontend should be organized by business module, not only by technical component type. Each module should own its pages, components, CSS module files, hooks, and type definitions where possible. This keeps the application maintainable as Preparer/Reconciler, Approver, Local Admin, and future roles expand.

### 18.1 UI Design Principle

The visual design should closely follow the provided BlackLine screenshots: compact enterprise layout, grey/white workspace, dense journal grids, left/top navigation behavior, role-aware action buttons, filter row styling, tabular data presentation, and clear certification sections.

Do not hardcode styling directly inside JSX except for unavoidable dynamic style values. Keep page-level and module-level CSS in separate `.module.css` files.

### 18.5 W3C/WCAG-Aligned HTML Attribute Rules

Every interactive element must have meaningful and stable attributes.

Rules:

```text

The label for attribute must match the input id.
Use aria-describedby when helper text or error text exists.
Use aria-invalid=true when a field has validation error.
Use button type="button" unless the button submits a form.
Use semantic elements: header, nav, main, section, table, button, form, label.
Avoid div-only interactive controls.
```

## 23. Key Implementation Rules

1. Journal source file parser must use tab delimiter `\t`.
2. Source journal parser must expect exactly 27 fields.
3. One user can have multiple roles.
4. User must choose active role from top-right dropdown.
5. Dropdown must show only roles assigned to the logged-in user.
6. Same user cannot be Preparer/Reconciler and Approver for the same journal.
7. Period `MM/YYYY` is the primary mandatory top filter.
8. Period filter exists mainly for performance and fast UI rendering.
9. Secondary filters appear below the period filter and above the grid.
10. Secondary auto-filter triggers only when input length is more than 2 characters.
11. Use 500 ms debounce for secondary filters.
12. Supporting document upload should allow any file type.
13. Uploaded document content should be stored as PostgreSQL BYTEA in Phase 1.
14. Document download icon should trigger direct download.
15. Document preview icon should open a new tab.
16. If preview is unavailable, user should download the file.
17. Admin currency grid must be immutable in Phase 1.
18. Email notifications are not required in Phase 1.
19. SSO is not required in Phase 1.
20. Full user management screen is not required in Phase 1.
21. JDE text file Preparer field must be treated as Preparer ADID for assignment resolution.
22. Preparer ADID must resolve to `users.adid`.
23. Approver must be resolved from dependency mapping using Preparer ADID.
24. External role code `BLPREPARER` maps to internal role `PREPARER_RECONCILER`.
25. External role code `BLAPPROVER` maps to internal role `APPROVER`.
26. If upstream sends `BLAPPROVER`, normalize it to `BLAPPROVER`.
27. Admin dependency mapping screen must be viewable by `LOCAL_ADMIN`.
28. Dependency mapping screen filters must be UI-only and must not hit the database.
29. Admin file upload must be a two-step process: Upload first, Parse second.
30. Parse must be all-or-nothing. If any row fails validation, no journal data should be committed.
31. `PARSE_FAILED` must not create journal headers, lines, or assignments.
32. Use explicit transaction handling: flush first, commit only if flush succeeds, rollback on any validation or database failure.
33. Admin must receive notifications for Parsing, Parse Success, and Parse Failed.
34. Preparer/Reconciler decertify must revert `PENDING_APPROVER` back to `PENDING_PREPARER` and return the journal to the Preparer/Reconciler queue.
35. Approver has only Certify/Approve and Reject actions in Phase 1.
36. Approver approval closes the journal.
37. Approver rejection sends the journal back to the Preparer/Reconciler queue for review and recertification.
38. Main data grids must support client-side pagination.
39. Filtering and sorting must be applied before pagination.
40. Certify, Approve, Reject, and Decertify actions must always create audit trail records.
41. If audit logging fails, the full workflow action must rollback.
42. Audit trail must show who acted, active role, old status, new status, action, comments/reason, and timestamp.
43. All protected APIs must require JWT Bearer token authentication.
44. Active role must be stored in JWT and validated against `user_session`.
45. Role switch must be backend-validated and must issue a new access token.
46. Frontend route guards are required but are not sufficient without backend authorization.
47. Journal actions must validate both active role and journal assignment.
48. All API failures must return structured error responses with error code, message, severity, details, and correlation ID.
49. UI must show proper popup/toast/dialog messages and must never show raw stack traces.
50. Error codes, success codes, and info codes must be centralized as enums.
51. Frontend must use a shared notification module instead of hardcoded page-level messages.
52. Future SFTP/S3/JDE integrations should be added through new infrastructure implementations without changing core workflow logic.

## 28. Admin Upload and Parse Transaction Rules

This section defines the mandatory transaction behavior when Local Admin uploads and parses the JDE journal file.

### 28.1 Two-Step Upload and Parse Lifecycle

The Admin upload flow must be implemented as two separate actions:

```text
Step 1: Upload File
Step 2: Parse File
```

Upload must only store the file and metadata. It must not create journal headers, journal lines, assignments, certifications, or audit records related to parsed journal data.

```text
Local Admin uploads JDE file
        |
        v
System stores file_content in journal_file_load
        |
        v
journal_file_load.status = UPLOADED
        |
        v
Admin clicks Parse
        |
        v
Parser validates complete file
        |
        v
If all validations pass, database transaction creates journal records
        |
        v
If any validation fails, rollback and do not populate journal data
```

### 28.2 File Load Status Values

The file load status should support these values:

```text
UPLOADED
PARSING
PARSED_SUCCESSFULLY
PARSE_FAILED
FAILED
```

Do not use `PARSE_FAILED` for Phase 1 journal creation because partial database population is not allowed.

If row-level errors occur, the final status should be:

```text
PARSE_FAILED
```

Reason:

```text
If the file has any parse or validation error, no journal header, journal line, or journal assignment data should be committed.
```

### 28.3 All-or-Nothing Parse Rule

Parsing must follow an all-or-nothing rule.

```text
If all rows are valid:
    Commit all journal headers, journal lines, assignments, totals, and audit logs.

If any row is invalid:
    Roll back the full transaction.
    Do not insert or update journal header data.
    Do not insert or update journal line data.
    Do not insert or update journal assignment data.
    Store parse errors against the file load.
    Notify the user that parse failed.
```

This avoids partial journals appearing in Preparer/Reconciler or Approver queues.

### 28.4 Validation Must Happen Before Database Write

The parser should perform these validations before writing business journal data:

```text
Validate file can be decoded.
Validate delimiter is tab.
Validate each row has exactly 27 columns.
Validate required fields are present.
Validate Amount is numeric.
Validate GLDate and BatchDate are valid dates.
Validate Preparer ADID exists in users.adid.
Validate dependency mapping exists for Preparer ADID.
Validate Approver ADID exists in users.adid.
Validate Preparer user and Approver user are different.
Validate currency conversion rate exists for the journal currency and period.
Validate duplicate journal grouping does not conflict with existing data.
```

Only after these validations pass should the application start creating journal headers, journal lines, assignments, totals, and audit logs.

### 28.5 Transaction Commit Rule

Database writes during parse must be wrapped in one explicit transaction.

Required rule:

```text
Flush first.
If flush succeeds, commit.
If flush fails, rollback.
If any exception occurs, rollback.
```

Recommended SQLAlchemy pattern:

```python
async def parse_journal_file(file_load_id: str, current_user: CurrentUser):
    async with session.begin():
        try:
            file_load = await file_load_repository.find_by_id(file_load_id)
            file_load.status = FileLoadStatus.PARSING
            await session.flush()

            validation_result = parser.validate(file_load.file_content)

            if validation_result.has_errors:
                file_load.status = FileLoadStatus.PARSE_FAILED
                file_load.error_message = validation_result.error_summary
                await parse_error_repository.save_all(validation_result.errors)
                await session.flush()
                raise ParseValidationException(validation_result.error_summary)

            journals = parser.to_journals(validation_result.rows)

            await journal_header_repository.save_all(journals.headers)
            await journal_line_repository.save_all(journals.lines)
            await journal_assignment_repository.save_all(journals.assignments)
            await audit_repository.save_all(journals.audit_logs)

            file_load.status = FileLoadStatus.PARSED_SUCCESSFULLY
            file_load.valid_rows = validation_result.valid_rows
            file_load.invalid_rows = 0
            file_load.journals_created = len(journals.headers)

            await session.flush()
            # Commit happens automatically when context exits successfully.

        except Exception:
            await session.rollback()
            raise
```

Important implementation note:

```text
Do not commit after every row.
Do not commit after every journal.
Do not commit before all headers, lines, assignments, totals, audit records, and file status updates are flushed successfully.
```

### 28.6 Parse Error Storage

Because journal business data must not be populated on parse failure, store errors separately at the file-load level.

Add table:

```sql
CREATE TABLE journal_file_parse_error (
    id BIGSERIAL PRIMARY KEY,
    parse_error_id VARCHAR(100) UNIQUE NOT NULL,
    file_load_id VARCHAR(100) NOT NULL REFERENCES journal_file_load(file_load_id),
    row_number INTEGER,
    field_name VARCHAR(255),
    error_code VARCHAR(100) NOT NULL,
    error_message TEXT NOT NULL,
    raw_line TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

This table allows the Admin to see exactly why parsing failed without creating partial journal records.

## 31. Decertify, Rejection, Approval, and Pagination Rules

This section explicitly defines the final Phase 1 workflow behavior for Preparer/Reconciler decertification, Approver approval/rejection, and grid pagination.

### 31.1 Preparer/Reconciler Decertify Rule

Preparer/Reconciler can decertify only after the journal has been certified by the Preparer/Reconciler and sent to the Approver, but before the Approver has approved or rejected it.

Allowed status for Preparer/Reconciler decertify:

```text
PENDING_APPROVER
```

When Preparer/Reconciler clicks `Decertify`:

```text
Journal is pulled back from the Approver queue.
Approver assignment is no longer actionable.
Preparer/Reconciler assignment is reopened.
Journal status is reverted to PENDING_PREPARER.
Journal appears again in Preparer/Reconciler dashboard grid for the same period.
Preparer/Reconciler can review, update comments/documents/hyperlinks, and certify again.
A decertification record is inserted.
An audit log is inserted.
```

Recommended status transition:

```text
PENDING_APPROVER
        |
        | Preparer/Reconciler clicks Decertify
        v
PENDING_PREPARER
```

Recommended assignment transition:

```text
Preparer/Reconciler assignment: COMPLETED -> ASSIGNED or IN_PROGRESS
Approver assignment: ASSIGNED -> SKIPPED or ASSIGNED but inactive until recertified
```

For Phase 1, use this simple approach:

```text
Preparer/Reconciler assignment = IN_PROGRESS
Approver assignment = ASSIGNED
Journal status = PENDING_PREPARER
```

The Approver dashboard must stop showing the journal immediately after the decertify action because the journal no longer has status `PENDING_APPROVER`.

### 31.2 Preparer/Reconciler Decertify API

```http
POST /api/v1/journals/{journalId}/decertify
```

Request:

```json
{
  "reason_code": "PREPARER_REVISION_REQUIRED",
  "comments": "Need to update supporting document before approval."
}
```

Response:

```json
{
  "journal_id": "JRN001",
  "previous_status": "PENDING_APPROVER",
  "current_status": "PENDING_PREPARER",
  "message": "Journal decertified and returned to Preparer/Reconciler queue."
}
```

### 31.3 Preparer/Reconciler Decertify Validation

Before decertifying, backend must validate:

```text
Logged-in user has active role PREPARER_RECONCILER.
Logged-in user is assigned as Preparer/Reconciler for the journal.
Journal status is PENDING_APPROVER.
Approver has not already certified or rejected the journal.
Journal is not CLOSED.
Journal is not already REJECTED.
Reason/comment is captured if configured as mandatory.
```

If validation fails, return an error message such as:

```text
This journal cannot be decertified because it is no longer pending approval.
```

### 31.4 Approver State Rule

Approver has only two business actions for Phase 1:

```text
Approve/Certify
Reject
```

Approver should not have the same decertify flow as Preparer/Reconciler in Phase 1.

Approver action mapping:

```text
PENDING_APPROVER -> Certify or Reject
CLOSED           -> View only
REJECTED         -> View only
```

### 31.5 Approver Approval Rule

When Approver certifies/approves:

```text
Approver certification record is inserted.
Approver assignment is marked COMPLETED.
Journal status is updated to CLOSED.
Audit log is inserted.
Journal appears in Approver grid as View only if closed records are included for the selected period.
Journal should not appear in Preparer/Reconciler actionable queue.
```

Recommended status transition:

```text
PENDING_APPROVER
        |
        | Approver certifies
        v
CLOSED
```

### 31.6 Approver Rejection Rule

When Approver rejects:

```text
Reject reason is mandatory.
Comment is mandatory if reason = OTHER, or if configured.
Rejection certification record is inserted.
Approver assignment is marked REJECTED.
Preparer/Reconciler assignment is reopened.
Journal status is updated to REJECTED.
Audit log is inserted.
Journal returns to Preparer/Reconciler dashboard grid for the selected period.
Preparer/Reconciler can review, update evidence, and certify again.
```

Recommended status transition:

```text
PENDING_APPROVER
        |
        | Approver rejects
        v
REJECTED
        |
        | Preparer/Reconciler recertifies
        v
PENDING_APPROVER
```

Recommended assignment transition on rejection:

```text
Approver assignment: ASSIGNED or IN_PROGRESS -> REJECTED
Preparer/Reconciler assignment: COMPLETED -> IN_PROGRESS
```

### 31.7 Dashboard Action Mapping After These Rules

Preparer/Reconciler dashboard action mapping:

```text
PENDING_PREPARER     -> Cert
PREPARER_IN_PROGRESS -> Cert
REJECTED             -> Cert
PENDING_APPROVER     -> View + Decertify
CLOSED               -> View
```

Approver dashboard action mapping:

```text
PENDING_APPROVER -> Cert
CLOSED           -> View
REJECTED         -> View
```

### 31.8 Pagination Requirement

All main data grids must support pagination similar to the reference screenshots.

Pagination applies to:

```text
Preparer/Reconciler dashboard grid
Approver dashboard grid
Admin uploaded file processing grid
Admin dependency mapping grid
Admin currency conversion grid
Journal line item grid if line count is large
Audit trail grid if record count is large
Supporting document grid if document count is large
```

### 31.9 Pagination Behavior

Period selection loads the period-level dataset from the backend. Pagination is then handled in the UI for Phase 1.

```text
Period filter -> backend/database hit
Pagination -> UI only on already-loaded rows
Column filters -> UI only on already-loaded rows
Sorting -> UI only on already-loaded rows unless later configured otherwise
```

Default pagination configuration:

```text
Default page size: 25
Allowed page sizes: 10, 25, 50, 100
Show current page number
Show total loaded records
Show range text, for example: Showing 1-25 of 143
Provide First, Previous, Next, Last controls
```

### 31.10 Pagination and Filtering Interaction

Filtering must be applied before pagination.

Processing order in UI:

```text
1. Load rows for selected period from backend.
2. Apply client-side column filters.
3. Apply client-side sorting if selected.
4. Apply pagination to the filtered/sorted rows.
5. Render current page rows.
```

Example:

```text
Loaded period rows: 300
After column filter: 42
Page size: 25
Page 1 shows rows 1-25
Page 2 shows rows 26-42
```

### 31.11 Pagination Component Requirement

Create reusable pagination components:


The journal grid should consume pagination like this:

```text

    -> all period rows
    -> useJournalLocalFilters

    -> render visible rows
```

### 31.12 Pagination DOM ids and names

Use stable, meaningful ids and names:

```tsx

```

### 31.13 Key Rule

```text
Do not perform database pagination in Phase 1 except for the initial period-level load if the dataset becomes too large later.
```

For Phase 1, period-level loading plus client-side filtering and pagination keeps the UI simple and close to the reference grid behavior.

## 32. Mandatory Audit Trail Logging for All Workflow Actions

Every workflow action must be captured in the audit trail. This is mandatory for Phase 1 and should align with the audit/certification trace behavior shown in the provided reference screenshots.

### 32.1 Actions That Must Be Audited

The following actions must always create an audit record:

```text
Preparer/Reconciler Certify
Approver Certify / Approve
Approver Reject
Preparer/Reconciler Decertify
Journal file upload
Journal file parse started
Journal file parse success
Journal file parse failed
Supporting document upload
Supporting document view/download, optional but recommended
Comment added
Hyperlink added
Role switch, optional but recommended for troubleshooting
```

For the core certification workflow, these four actions are mandatory:

```text
CERTIFY
APPROVE
REJECT
DECERTIFY
```

### 32.2 Audit Trail Principle

The audit trail must answer these questions for every action:

```text
Who performed the action?
Which role was active when the action was performed?
What journal was affected?
What action was performed?
What was the old status?
What is the new status?
When was the action performed?
What comments/reason were provided?
What supporting metadata was captured?
```

### 32.3 Audit Record Creation Rule

For every successful workflow action, the application must write:

```text
1. Business transaction update
2. Certification/action record where applicable
3. Audit trail record
4. Commit only if all required records flush successfully
```

If the audit trail record fails to flush, the full action must rollback.

Required transaction rule:

```text
No workflow action is complete unless the audit log is successfully written.
```

### 32.4 Mandatory Audit Events

#### Preparer/Reconciler Certify


### 32.8 Transaction Pattern for Workflow Actions

All workflow action application services must follow this structure:

```python
async def certify_journal(journal_id: str, current_user: CurrentUser):
    async with session.begin():
        try:
            journal = await journal_repository.get_for_update(journal_id)
            old_status = journal.status

            # Validate active role, assignment, and current status.
            workflow_service.validate_certify(journal, current_user)

            # Update business state.
            journal.status = JournalStatus.PENDING_APPROVER
            await assignment_repository.mark_completed(journal_id, current_user.user_id)

            # Insert certification record.
            certification = JournalCertification(...)
            await certification_repository.save(certification)

            # Insert audit trail record.
            audit = JournalAuditLog(
                journal_id=journal_id,
                action_type="PREPARER_CERTIFIED",
                old_status=old_status,
                new_status=journal.status,
                performed_by=current_user.user_id,
                performed_role=current_user.active_role,
                message="Journal certified by Preparer/Reconciler and sent for approval.",
            )
            await audit_repository.save(audit)

            # Flush all changes before commit.
            await session.flush()
            # Commit happens when context exits successfully.

        except Exception:
            await session.rollback()
            raise
```

```text

Do not leave the journal in a partially updated state.
```

Recommended error message:

```text

```

```text

Decertified successfully and returned to Preparer/Reconciler queue.
```

If any part fails before commit, show an error notification:

```text
Action failed. No changes were saved.
```

### 32.11 Audit Trail Acceptance Criteria

A workflow action is acceptable only if:

```text
The journal status changed correctly.
The assignment status changed correctly.
The certification/rejection/decertification record was created.
The audit trail record was created.
The user received a success notification.
The Audit Trail section displays the event.
If any step failed, all changes were rolled back.
```

## 33. Security Architecture: JWT Bearer Token, Session Management, and Authorization

Phase 1 must include proper authentication and authorization even though enterprise SSO is deferred. The application must not rely only on frontend route hiding because any user can manually type a URL and attempt to access restricted pages.

Security principle:

```text
Authentication confirms who the user is.
Authorization confirms what the user is allowed to do.
```

A user may be authenticated but still not authorized to:

```text
Open Admin pages
Upload JDE journal files
View dependency mappings
View currency conversion screen
Certify a journal not assigned to them
Approve a journal not assigned to them
View another user's restricted journal task
```

### 33.1 Phase 1 Authentication Model

Use JWT Bearer Token authentication for Phase 1 demo login.

Login endpoint:

```http
POST /api/v1/auth/login
```

Successful response:

```json
{
  "access_token": "<jwt-access-token>",
  "refresh_token": "<jwt-refresh-token>",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

All secured API requests must include:

```http
Authorization: Bearer <jwt-access-token>
```

### 33.2 JWT Payload

The access token should include only the minimum required identity and authorization context.

Recommended JWT claims:

```json
{
  "sub": "USR001",
  "adid": "SUNDARN1",
  "display_name": "Demo User One",
  "email": "demo.user1@example.com",
  "active_role": "PREPARER_RECONCILER",
  "session_id": "SES001",
  "iat": 1780000000,
  "exp": 1780003600
}
```

Do not store sensitive data such as password hashes or confidential profile details inside the JWT.

### 33.3 Refresh Token

Use a refresh token so the user does not need to log in again while actively working.

Refresh endpoint:

```http
POST /api/v1/auth/refresh-token
```

Request:

```json
{
  "refresh_token": "<jwt-refresh-token>"
}
```

Response:

```json
{
  "access_token": "<new-jwt-access-token>",
  "token_type": "Bearer",
  "expires_in": 3600
}
```

Recommended Phase 1 token timings:

```text
Access token validity: 30 to 60 minutes
Refresh token validity: 8 to 12 hours for demo usage
```

### 33.4 Active Role Switch Must Issue a New Token

When a user switches active role from the top-right dropdown, the change must not be done only in React state. The backend must validate the role and issue a new JWT with the updated active role.

Endpoint:

```http
POST /api/v1/auth/switch-role
```

Request:

```json
{
  "role_code": "APPROVER"
}
```

Backend behavior:

```text
Validate JWT.
Validate session is active.
Validate requested role belongs to the logged-in user.
Update user_session.active_role_code.
Issue a new access token with active_role = requested role.
Return the updated token and user context.
```

Response:

```json
{
  "access_token": "<new-jwt-access-token>",
  "token_type": "Bearer",
  "active_role": "APPROVER",
  "roles": [
    "PREPARER_RECONCILER",
    "APPROVER"
  ]
}
```

### 33.5 Session Validation

The existing `user_session` table must be used to validate active sessions.

Every secured API request should validate:

```text
JWT signature is valid.
JWT is not expired.
session_id exists in user_session.
user_session.is_active = true.
user_session.expires_at is not expired.
active_role in JWT matches active_role_code in user_session.
user still has the active role in user_roles.
```

If any validation fails, return:

```http
401 Unauthorized
```

or

```http
403 Forbidden
```

depending on the failure.

### 33.6 Authorization Layers

Authorization must be enforced in three layers.

#### Layer 1: Frontend Route Guard

Frontend route guards prevent users from casually navigating to unauthorized pages.

Examples:

```text
/admin/upload-journal requires LOCAL_ADMIN
/admin/dependency-mapping requires LOCAL_ADMIN
/admin/currency-rates requires LOCAL_ADMIN
/journals requires PREPARER_RECONCILER or APPROVER
```

If the user is not authorized, redirect to:

```text
/no-access
```

or show:

```text
Access denied
```

#### Layer 2: Backend API Role Authorization

Every API endpoint must validate the required role. Frontend checks are not sufficient.

Example role rules:

```text
Upload JDE file: LOCAL_ADMIN only
Parse JDE file: LOCAL_ADMIN only
View dependency mapping: LOCAL_ADMIN only
View currency conversion: LOCAL_ADMIN only
Work queue: PREPARER_RECONCILER or APPROVER based on active role
Certify as Preparer/Reconciler: PREPARER_RECONCILER only
Certify/Reject as Approver: APPROVER only
Decertify as Preparer/Reconciler: PREPARER_RECONCILER only
```

Recommended backend pattern:

```python
@router.post("/journal-files/{file_load_id}/parse")
async def parse_file(
    file_load_id: str,
    current_user: CurrentUser = Depends(require_role(RoleCode.LOCAL_ADMIN)),
):
    ...
```

#### Layer 3: Journal Assignment Authorization

Role alone is not enough. The user must also be assigned to the specific journal.

Example:

```text
A user with APPROVER role cannot approve every journal.
A user can approve only journals where journal_assignment.role_code = APPROVER and journal_assignment.assigned_user_id = logged-in user.
```

Required validation for journal actions:

```text
Check active role.
Check journal status.
Check assignment exists for journal_id + active_role + logged-in user.
Check assignment is actionable.
Check workflow transition is valid.
```

If assignment is missing, return:

```http
403 Forbidden
```

Message:

```text
You are not assigned to this journal.
```

### 33.7 Page Authorization Matrix

| Page | Required Active Role |
|---|---|
| Login | Public |
| Role Dashboard / Work Queue | PREPARER_RECONCILER or APPROVER |
| Journal Detail | Assigned PREPARER_RECONCILER or assigned APPROVER |
| Admin Upload Journal | LOCAL_ADMIN |

### 33.9 Frontend Token Storage Rule

Recommended Phase 1 approach:

```text
Store access token in memory when possible.
Use secure, httpOnly cookie for refresh token if backend/frontend deployment supports it.
Avoid storing long-lived tokens in localStorage.
```

If localStorage is used for demo simplicity, document it as a Phase 1 limitation and replace it before production.

### 33.10 No Direct Page Access Without Authorization

The user must not be able to navigate directly to restricted pages by typing URLs.

Examples that must be blocked:

```text

Unassigned user opens /journals/JRN001 -> Forbidden
User switches only React state to APPROVER without backend token -> Forbidden
Expired token opens any protected route -> Redirect to login
```

### 33.12 Security-Related Tables

The existing `user_session` table supports Phase 1 JWT session validation. Add refresh token tracking if refresh tokens are stored server-side.

```sql
CREATE TABLE user_refresh_token (
    id BIGSERIAL PRIMARY KEY,
    token_id VARCHAR(150) UNIQUE NOT NULL,
    session_id VARCHAR(150) NOT NULL REFERENCES user_session(session_id),
    user_id VARCHAR(100) NOT NULL REFERENCES users(user_id),
    token_hash VARCHAR(500) NOT NULL,
    issued_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP NOT NULL,
    revoked_at TIMESTAMP NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);
```

Never store raw refresh tokens in the database. Store a hash.

### 33.13 Logout Behavior

Logout endpoint:

```http
POST /api/v1/auth/logout
```

Logout should:

```text
Mark user_session.is_active = false.
Mark active refresh tokens as revoked.
Clear frontend auth state.
Redirect user to login.
```

### 33.14 Audit Security Events

The following security events should be logged either in `journal_audit_log` where journal-specific or a future `security_audit_log` where application-level:

```text
Login success
Login failure
Logout
Role switch
Unauthorized API access attempt
Forbidden journal access attempt
Token refresh
Session expiration
```

For Phase 1, journal-specific authorization failures can be captured in application logs. A dedicated `security_audit_log` table can be added later if needed.

### 33.15 Security Acceptance Criteria

Authentication and authorization are acceptable only if:

```text
All protected APIs require Bearer token.
All protected pages require valid frontend auth context.
Role switch generates a backend-validated token.
Admin pages are blocked for non-admin roles.
Journal detail is blocked for unassigned users.
Certify/Reject/Decertify validates active role and journal assignment.
Expired sessions are rejected.
Logout invalidates session and refresh token.
Frontend route protection and backend API protection both exist.
```

## 34. Centralized Error Handling, Success Messages, and Application Notifications

The application must not display raw technical exceptions directly on the UI. All API failures, validation failures, business rule failures, and unexpected system failures must be converted into structured API responses with stable error codes and user-friendly messages. The UI should render those messages through a reusable popup/toast/dialog notification module.

### 34.1 Error Handling Principle

```text
Do not throw raw backend errors on the UI.
Do not show stack traces to users.
Do not hardcode user-facing messages in many frontend components.
Do not duplicate the same message in multiple backend services.
Use centralized error codes, message keys, and notification components.
```

The backend should send:

```text
error_code
message
severity
details if needed
trace_id or correlation_id
```

The frontend should render:

```text
Success popup/toast
Error popup/toast
Warning popup/toast
Information popup/toast
Field-level validation messages where applicable
```

---

```python
from enum import Enum
```

Recommended UI rendering:

```text
SUCCESS -> green success popup/toast
ERROR   -> red error popup/dialog
WARNING -> amber warning popup/toast
INFO    -> blue/neutral information popup/toast
```

## 35.4 Folder Structure Rules

### Backend Rules

```text
Do not import infrastructure code into domain.
Use repository interfaces in domain and implementations in infrastructure.
Use service interfaces in domain and implementations in infrastructure.
Use application services for application orchestration.
Use controllers only for HTTP request/response handling.
Use schemas only for API request/response contracts.
Use DTOs for application layer transfer objects.
Use enums for workflow logic and message codes.
Use message catalog for user-facing messages.
Use exception handlers for API error responses.
```

### Frontend Rules

```text
Each module owns its pages, components, hooks, services, types, and styles.
Do not put module-specific CSS in global styles.
Do not hardcode API logic inside React components.
Do not hardcode repeated messages inside pages.
Use shared notification module for all success/error/info/warning messages.
Use shared API client for all backend calls.
Use shared pagination and filter hooks where possible.
Use page-specific and component-specific CSS modules.
Do not use external product names in folders, files, comments, CSS, or UI labels.
```

## 36. Enterprise Controller, Service, and Implementation Naming Convention

The application should use clear enterprise naming instead of the `use_cases` folder name. The folder name `use_cases` is common in Clean Architecture, but for this project the preferred enterprise naming is:

```text
Controller -> Application Service Interface -> Application Service Implementation -> Domain Service Interface -> Infrastructure Service Implementation -> Repository Interface -> Repository Implementation
```

### 36.1 Final Naming Decision

Do not use this folder name:

```text
backend/app/application/use_cases/
```

Use this instead:

```text
backend/app/application/services/
```

Reason:

```text
The term Application Service is more enterprise-friendly and aligns better with the controller/service/implementation style requested for this project.
```

### 36.2 Responsibility Split

#### Controller

Controllers handle HTTP only.

Responsibilities:

```text
Read request
Validate request schema
Get current user context
Call application service
Return API response
Do not contain business workflow logic
Do not directly access repositories
Do not directly parse files
Do not directly update journal status
```

Example folder:

```text
backend/app/api/v1/controllers/certification_controller.py
```

#### Application Service Interface

Application service interfaces define orchestration contracts.

Example folder:

```text
backend/app/application/services/certify_journal_service.py
```

Example class naming:

```text
ICertifyJournalService
IRejectJournalService
IDecertifyJournalService
IParseJournalFileService
IGetWorkQueueByPeriodService
```

#### Application Service Implementation

Application service implementations orchestrate the full business workflow.

Example folder:

```text
backend/app/application/services/impl/certify_journal_service_impl.py
```

Example class naming:

```text
CertifyJournalServiceImpl
RejectJournalServiceImpl
DecertifyJournalServiceImpl
ParseJournalFileServiceImpl
GetWorkQueueByPeriodServiceImpl
```

Responsibilities:

```text
Validate workflow status
Validate active role
Validate journal assignment
Start transaction
Call domain services
Call repositories
Create audit record
Flush
Commit or rollback
Return application DTO
```

#### Domain Service Interface

Domain services contain reusable business rules that are not tied to HTTP, database, or UI.

Example folder:

```text
backend/app/domain/services/certification_workflow_service.py
```

Example class:

```text
ICertificationWorkflowService
```

#### Infrastructure Service Implementation

Infrastructure services implement technical details such as token generation, blob storage, message mapping, parser implementation, or database-specific operations.

Example folder:

```text
backend/app/infrastructure/services/certification_workflow_service_impl.py
```

Example class:

```text
CertificationWorkflowServiceImpl
```

### 36.5 Naming Rules

Use these naming conventions consistently:

```text
Controller file: certification_controller.py
Controller class: CertificationController or FastAPI router module

Application service interface file: certify_journal_service.py
Application service interface class: ICertifyJournalService

Application service implementation file: certify_journal_service_impl.py
Application service implementation class: CertifyJournalServiceImpl

Domain service interface file: certification_workflow_service.py
Domain service interface class: ICertificationWorkflowService

Infrastructure service implementation file: certification_workflow_service_impl.py
Infrastructure service implementation class: CertificationWorkflowServiceImpl

Repository interface file: journal_header_repository.py
Repository interface class: IJournalHeaderRepository

Repository implementation file: journal_header_repository_impl.py
Repository implementation class: JournalHeaderRepositoryImpl
```

### 36.6 Rule for Controllers

Controllers must not instantiate implementation classes directly. They should receive application services through dependency injection.

Correct:

```text
controller -> interface -> injected implementation
```

Incorrect:

```text
controller -> new CertifyJournalServiceImpl()
```

### 36.7 Rule for Application Services

Application services contain orchestration logic, not low-level technical logic.

They can:

```text
Call repositories
Call domain services
Call infrastructure services through interfaces
Manage transaction boundaries
Create audit records
Return DTOs
```

They should not:

```text
Contain raw SQL
Contain UI logic
Build HTML
Access request objects directly
Import FastAPI router classes
Hardcode user-facing messages
```

## 25. Reference Notes for UI Standards

- HTML `id` values must be unique within a document, so page and component ids should be generated or named carefully to avoid duplicate ids in repeated grid rows.
